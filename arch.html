同一个 Agent 循环，四种编排容器

把砼智销的「5 步有界询价循环」原样搬进 LangGraph、LangChain、LlamaIndex、AutoGen， 业务规则一行不改：工具注册表、权限裁决、合法动作序列、账本写入全部复用原模块。 四个实现共用同一个循环体，差异只可能来自编排容器本身。 下面的数字由 tools/build_arch_data.py 从实验产物编译生成，页面不写死任何指标。

容器成本：为「可持久化」付了多少钱

参照系是裸循环——同一个 RfqLoop，用最朴素的 while 驱动，不引入任何框架。 测量按轮配对：每轮先跑裸循环、紧接着跑框架，先算单题差值再聚合，抵消进程级漂移。 括号内为配对差值的 95% 置信区间；区间跨 0 记为"噪声内"，不当作差异。

四维对照

业务等价 = 与原生 prepare_rfq() 的业务快照逐字段比对；依赖包与体积 = 各框架独立 venv 的客观代价。

口径与效度：这组数字不能证明什么

对照实验最容易犯的错，是拿两个不同工作量的实现比耗时。下面几条是主动披露的边界。

一、没有用 LLM 做动作选择。 原实现的 prepare_rfq(model_propose=None) 走的是 DETERMINISTIC_FALLBACK：取合法动作序列的第一个。四个容器完整复现了这一语义， 所以本页比较的是编排与状态管理，不是「谁的 Agent 更聪明」。工具选择策略若换成 LLM， 结论需要重测。
二、「对原生」的差值不是一个干净的基准。 原生 prepare_rfq 每步还要算 _planner_observation、写 planner_input_summary 的 SHA-256 摘要、 调 business_tool_definitions——这些是为喂 LLM 规划器准备的记账。搬运到容器里的循环体没有这些步骤， 直接对比会把「少做的记账」误读成「框架更快」。因此本页只用裸循环做耗时参照。
三、跨进程续跑只有一家做了实测。 LangGraph 用子进程 os._exit 制造真崩溃后恢复， 有产物为证；其余三家只验证了「状态能否序列化成字节」，标为 not_demonstrated。有 API 不等于已验证，不把前者写成后者。
四、样本量与延迟口径。 每次运行都用全新 SQLite 库，因此包含建库成本（四家相同，被配对抵消）。 延迟为单机、无并发、冷库条件，不是线上 P95；生产压测另见评测中心的 HTTP 池结论。
